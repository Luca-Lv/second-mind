# 授权说明

## 一句话

这个仓库**不是开源项目**，而是「源码可见（source-available）」：能看、能自己部署用，但不能改、不能再分发、不能拿去做产品。

许可证正文在 [LICENSE](../LICENSE)，英文为准。本文只解释它为什么这么写、边界在哪、以及它挡不住什么。

## 为什么撤掉了 MIT

MIT 的原文是「允许任何人免费使用、复制、修改、合并、发布、再许可、销售」。也就是说，MIT 恰好允许了你最不想要的三件事：

- 别人 fork 一份改个名字，当成自己的产品发布
- 别人把代码打包进自己的商业产品去卖
- 别人把改过的版本再分发，且不需要告诉你

只要仓库里放着 MIT 的 `LICENSE`，你在 README 里写「禁止商用」是没有法律效力的——许可文本冲突时，授权范围以许可为准。所以必须是**换掉许可证**，而不是加一句声明。

## 三个必须知道的法律现实

**1. 公开仓库挡不住 GitHub 上的 Fork。**

GitHub 的服务条款规定，公开仓库的作者授予 GitHub 用户「查看与 Fork」的权利。这是平台层面的授权，你的许可证改不了它。你能做的是：Fork 出去的副本**只享有你许可证给的权利**——它不能部署给别人用、不能改、不能商用，你可以要求 GitHub 下架侵权仓库。若连 Fork 都不能接受，唯一彻底的办法是**不公开源码**（见下）。

**2. 「不能复制」在技术上不成立。**

运行程序必然要把代码复制进内存、复制到服务器磁盘。所以许可证的写法是「为构建、运行、备份所必需的复制被允许，其余复制被禁止」。这不是妥协，是任何软件许可都必须这样写，否则连正常使用都算侵权。

**3. 许可要靠你自己执行。**

许可证不是防盗门，是打官司时的依据。发现侵权时你可以：

- 向托管平台投诉（GitHub 的 DMCA / 版权投诉流程），要求下架
- 发律师函要求停止使用
- 起诉索赔

举证通常靠代码相似度、文件结构、注释与命名的一致性。为提高可追溯性，建议保留版权头、提交历史，必要时在构建产物里嵌入版权声明。

## 如果这还不够严

| 方案 | 效果 | 代价 |
|---|---|---|
| **只发布构建产物**（`dist/` 或 Docker 镜像）+ 使用条款 | 别人拿不到源码，改编成本极高 | 无法被检索、无法被学习，社区不会增长 |
| **私有仓库 + 邀请** | 完全可控 | 没有公开曝光 |
| **双许可**（个人免费 / 商用付费） | 既开放又收费 | 需要能识别谁在商用 |
| **注册商标**（"second mind"） | 名称层面的保护 | 费用与周期，且不保护代码 |

当前选择是「公开源码 + 严格许可」，用可检索性换传播，用许可条款约束使用。

## 贡献与权利归属

许可第 5 条要求：提交 PR 即视为你**永久、不可撤销地**授权作者使用、修改、再许可你的贡献，并放弃阻止作者行使这些权利的著作人身权。

这一条不是霸王条款，而是必需的：如果每个贡献者保留自己那部分的权利，作者就无法统一地许可（或出售许可）整个项目，后期会变成「谁都能否决」的局面。常见做法是 CLA（贡献者许可协议）或 DCO（开发者原创声明），本项目用 LICENSE 内的条款代替单独的 CLA 文件。

如果你不接受这一条，请不要提交 PR；提 Issue 描述问题同样有价值。

## 第三方依赖不受本许可约束

React、d3-force、zustand、Vite 等依赖仍按各自许可（多为 MIT）授权。你不能用本项目的许可证去限制别人对这些库的使用，本项目也无权这么做。`NOTICE` 里列了主要依赖及其许可。

这也是为什么「完全禁止复制」不可能：即使代码全是原创，打包产物里也含有 MIT 库的代码，那些部分必须保留其许可声明。

## 变更历史与一条时间线

- `0.1.0` 起草时用的是 MIT（模板默认），随后按作者要求改为 Second Mind Source-Available License v1.0。
- **这个仓库尚未推送到任何公开平台**，因此没有第三方已按 MIT 获得授权，切换是干净的。
- 一旦以 MIT 公开过，那个版本对已获得副本的人**永久**是 MIT，无法收回——只能对新版本换许可。这是许可证不可撤销性的直接后果，也是「先定许可再发布」的原因。
