# 授权说明

## 一句话

这个仓库**不是开源项目**，而是「源码可见（source-available）」：能看、能构建、能自己部署起来用（**包括部署成公开可访问的网站**），但不能改、不能再分发、不能拿去做产品。

许可证正文在 [LICENSE](../LICENSE)，英文为准。本文只解释它为什么这么写、边界在哪、以及它挡不住什么。

## 为什么撤掉了 MIT

MIT 的原文是「允许任何人免费使用、复制、修改、合并、发布、再许可、销售」。也就是说，MIT 恰好允许了你最不想要的三件事：

- 别人 fork 一份改个名字，当成自己的产品发布
- 别人把代码打包进自己的商业产品去卖
- 别人把改过的版本再分发，且不需要告诉你

只要仓库里放着 MIT 的 `LICENSE`，你在 README 里写「禁止商用」是没有法律效力的——许可文本冲突时，授权范围以许可为准。所以必须是**换掉许可证**，而不是加一句声明。

| ✅ 可以 | **部署成公开可访问的站点**，让任何人打开都能用（非商业、自用，见下节条件） |

「公开可访问」和「再分发」看起来冲突，实际不冲突，这是本次放宽时特意写清的一处：

- 你把站点跑起来，别人用浏览器打开，**这不叫分发**。许可第 2(f) 条明确写了：部署时向访客浏览器传输编译产物，不构成 Distribution。
- 但你把 `dist/` 打包上传到网盘、发 Release、传到别的代码托管，**那就是分发**，被禁止。
- 访客只能使用你跑着的那个站点，**不因此获得任何代码层面的权利**。

## 公开部署必须满足的四个条件

许可第 2(c) 条把这四个条件写成并列项，缺一条就超范围：

1. **你个人（或家庭）运营**，服务于你自己的用途——不是替别人运营、不是代管。
2. **不把站点本身当成要卖的东西**——不销售、不营销、不作为产品呈现，也不对外提供托管、代管或有偿支持服务。注意：**「谁都能打开」不等于「对外提供服务」**，第 2(f) 条专门写了这一句，「公开可访问」本身不使你成为服务提供方。
3. **不产生收入**——不对访问、会员或任何功能收费。挂广告、放收款码都算产生收入，都不行。
4. **保留版权与许可声明**——设置页底部那行 `© 2026 Lv Ke · second mind` 不能删。删了直接违反第 3(e) 条，授权自动终止。

违反任一条款，授权**自动终止**，须立即停止使用并删除全部副本。想合法地改编或商用，只有一条路：联系作者单独授权（双许可）。

## 「非商业」的灰色地带

「非商业」在许可里被定义成「不以商业优势或金钱报酬为目的」（第 1 条 "Commercial"）。落到具体场景：

| 场景 | 判定 | 理由 |
|---|---|---|
| 部署在自己域名上，只有自己用 | ✅ 允许 | 典型 Personal Use |
| 链接发给朋友，他们注册使用 | ✅ 允许 | 非商业、不收费、不运营服务 |
| 发在小红书 / 少数派上：「我自己搭的，你们可以试试」 | ⚠️ 擦边界 | 属于分享个人部署，但已经接近「对外提供」。保留版权声明、不收费、不承诺维护，风险低 |
| 挂 AdSense 或任何广告 | ❌ 不允许 | 产生收入即构成 Commercial |
| 挂「赞助我」/ 收款码 | ❌ 不允许 | 同上，金钱报酬 |
| 公司内网给同事用 | ❌ 不允许 | 许可明确把「营利实体的业务内使用」算作 Commercial |
| 写成产品页、起个新名字、加客服、收会员费 | ❌ 不允许 | 已经是产品/服务，且违反 3(f) 名称条款 |
| 改成自己想要的样式再部署 | ❌ 不允许 | 修改本身被禁止，与是否公开无关 |

这张表是我对条款的解读，**不是条款本身**。真起争议时以 [LICENSE](../LICENSE) 英文正文为准；如果你需要一条明确规则来判某个具体场景，可以让我把它直接写进许可里，这样比留在解释文档里有效力。

关于名称，有一处容易混淆：页脚必须保留 `© 2026 Lv Ke · second mind`（这是第 3(e) 条要求的版权声明），但你不能把部署出去的站点**对外称作** "second mind" 官方版、授权版，也不能用这个名字去背书或暗示与作者有关联（第 3(f) 条）。保留声明是义务，借名字是越界。

## 三个必须知道的法律现实

**1. 公开仓库挡不住 GitHub 上的 Fork。**

GitHub 的服务条款规定，公开仓库的作者授予 GitHub 用户「查看与 Fork」的权利。这是平台层面的授权，你的许可证改不了它。你能做的是：Fork 出去的副本**只享有你许可证给的权利**——它可以被构建、被非商业地部署，但不能改、不能商用、不能再分发源码，更不能改名当成自己的产品。违反之后你可以要求 GitHub 下架侵权仓库。若连 Fork 都不能接受，唯一彻底的办法是**不公开源码**（见下）。

**2. 「不能复制」在技术上不成立。**

运行程序必然要把代码复制进内存、复制到服务器磁盘。所以许可证的写法是「为构建、运行、备份所必需的复制被允许，其余复制被禁止」。这不是妥协，是任何软件许可都必须这样写，否则连正常使用都算侵权。

**3. 许可要靠你自己执行。**

许可证不是防盗门，是打官司时的依据。发现侵权时你可以：

- 向托管平台投诉（GitHub 的 DMCA / 版权投诉流程），要求下架
- 发律师函要求停止使用
- 起诉索赔

举证通常靠代码相似度、文件结构、注释与命名的一致性。为提高可追溯性，建议保留版权头、提交历史，必要时在构建产物里嵌入版权声明。

## 如果这还不够严

| 方案 | 效果 | 代价 |
|---|---|---|
| **只发布构建产物**（`dist/` 或 Docker 镜像）+ 使用条款 | 别人拿不到源码，改编成本极高 | 无法被检索、无法被学习，社区不会增长 |
| **私有仓库 + 邀请** | 完全可控 | 没有公开曝光 |
| **双许可**（个人免费 / 商用付费） | 既开放又收费 | 需要能识别谁在商用 |
| **注册商标**（"second mind"） | 名称层面的保护 | 费用与周期，且不保护代码 |

当前选择是「公开源码 + 严格许可」，用可检索性换传播，用许可条款约束使用。

## 贡献与权利归属

许可第 5 条要求：提交 PR 即视为你**永久、不可撤销地**授权作者使用、修改、再许可你的贡献，并放弃阻止作者行使这些权利的著作人身权。

这一条不是霸王条款，而是必需的：如果每个贡献者保留自己那部分的权利，作者就无法统一地许可（或出售许可）整个项目，后期会变成「谁都能否决」的局面。常见做法是 CLA（贡献者许可协议）或 DCO（开发者原创声明），本项目用 LICENSE 内的条款代替单独的 CLA 文件。

如果你不接受这一条，请不要提交 PR；提 Issue 描述问题同样有价值。

## 第三方依赖不受本许可约束

React、d3-force、zustand、Vite 等依赖仍按各自许可（多为 MIT）授权。你不能用本项目的许可证去限制别人对这些库的使用，本项目也无权这么做。`NOTICE` 里列了主要依赖及其许可。

这也是为什么「完全禁止复制」不可能：即使代码全是原创，打包产物里也含有 MIT 库的代码，那些部分必须保留其许可声明。

## 变更历史与一条时间线

- `0.1.0` 起草时用的是 MIT（模板默认），随后按作者要求改为 Second Mind Source-Available License v1.0。
- 同一版本内做过一次放宽：初稿只允许「本人与家庭使用的私人部署，不对外提供服务」；现在允许**非商业、自用的公开部署**，并为此新增 2(c) 的四项条件与 2(f) 的「部署不构成再分发」澄清。版本号未变，因为尚未发布，没有第三方持有旧文本。
- **这个仓库尚未推送到任何公开平台**，因此没有第三方已按 MIT 获得授权，切换是干净的。
- 一旦以 MIT 公开过，那个版本对已获得副本的人**永久**是 MIT，无法收回——只能对新版本换许可。这是许可证不可撤销性的直接后果，也是「先定许可再发布」的原因。
